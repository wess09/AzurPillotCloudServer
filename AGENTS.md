# Repository Guidelines

## Architecture

Go 1.26 / PostgreSQL API backend. Frontend lives in the separate private repository `wess09/AzurPilotCloudWeb` and deploys from GitHub directly to Cloudflare Pages. This repository and the main runtime must contain no frontend source or compiled assets.

- `cmd/server/`: dependency wiring, startup and graceful shutdown.
- `internal/database/`: shared GORM connection, typed query helpers and versioned ORM migrations.
- `internal/store/`: core persistence models and transactions.
- `internal/v3db/`: statistics and template-event metadata models; no template images.
- `internal/drops/`: structured ingestion, hourly aggregation and public queries.
- `internal/adminws/`: authenticated WebSocket RPC and change-only state subscriptions.
- `internal/httpapi/`: HTTP public/client APIs and management command dispatch.
- `internal/templatesync/`: idempotent mapping/status event receiver.
- `workers/`: announcement/update Worker templates; `public/`: generated JSON documents.

## Database rules

No handwritten SQL anywhere in application code, migrations, tests or maintenance tools. Do not use SQL files, raw execution methods, SQL string conditions, expression escape hatches, or handwritten aggregate expressions. Use GORM models, Migrator, typed `clause` predicates and the library's `gorm.io/gen/field` expressions. Column identifiers are allowed; database statements are generated by dependencies.

Keep response DTOs separate from persistence models. Append consecutive `database.Migration` steps for schema changes. Migration failures roll back; older binaries reject newer schema versions. The core and statistics domains share one production connection pool. Never reintroduce A/B recognition tables or template-image storage into the main service.

## Development and verification

`go run ./cmd/server`, `make build`, `docker compose up -d --build`. No Node or frontend build is needed here.

Format with `gofmt`; follow `.golangci.yml`. Use standard-library HTTP and GORM. Run `go vet ./...`, `go test -race -count=1 ./...` and the configured lint checks. `TEST_DATABASE_URL` enables core PostgreSQL integration tests; `TEMPLATE_TEST_DATABASE_URL` enables mapping/aggregation integration tests. Both must point to isolated test databases or schemas. Tests cover the no-raw-SQL invariant, migration rollback/restart, concurrency, validation and failures.

Management reads, writes and updates use `/api/v1/admin/ws`; no REST management handlers or HTTP polling. Public statistics use HTTP. Client template uploads and all template administration connect directly to the independent template service. Main handles only small mapping/status events. Frontend functional tests are in its own repository; do not test WebUI styles for this refactor.

## Commits and security

Create focused local commits after completing changes and necessary verification, unless the user explicitly says otherwise. PR descriptions state behavior, tests and relevant migration/configuration changes.

Consult `.env.example`. Never commit or print credentials. Empty `ADMIN_TOKEN` disables administration. Management authenticates in the first WebSocket frame, never in a URL. Validate exact browser origins. Retain publisher readback verification and graceful shutdown. A backend image contains only the binary and writable generated JSON output.
